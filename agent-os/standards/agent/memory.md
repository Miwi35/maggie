# Memory folder (ADR-011)

Maggie's memory is a folder of Markdown files per user, in an S3 bucket. **The files are the only truth**; Postgres holds a disposable index. Detailed spec: Linear « Spec : Mémoire vivante ». Code: `agent/app/memory/`, `agent/app/db/memory_index_*.py`.

## The folder
- Bucket prefix = the user's ULID (`sub` of the JWT): `<ULID>/Mémoire/…`. Every path goes through `app/memory/paths.py` — a name with `/`, `\`, `:`, `..` or a control character never reaches the bucket or the disk. Test every new entry point with `%2e%2e` and a separator.
- Generated files at the root say so on their first line and carry a seal (`<!-- sceau: … -->`): `LISEZMOI.md`, `AGENTS.md`, `sommaire.md`, `journal.md`. Regenerated only while the seal matches — an edit by the owner is kept.
- `Conversations/AAAA/MM/AAAA-MM-JJ HHhMM — sujet.md` are never rewritten. `Conflits/` holds the versions of Maggie set aside. Other folders hold fiches (a carte in YAML frontmatter: `id`, `resume`, `moments`, `personnes`, `evoque`, `alias`, `liens`, `sources`; then text). File name = title; `id` is the identity.

## The two layers (MAG-17)
- **Conversations, kept whole.** `app/memory/conversations.py` appends every message of a thread to its file as it is stored (`MessageRepository.create`, `update_context`, and before any memory tool) — never from a tool, never by the model: what the owner said in passing is on file even if Maggie calls nothing. Each message is headed `## AAAA-MM-JJ HHhMM — rôle`. `MemoryService.write` refuses to rewrite the messages of a conversation file: it may grow at the end, or have its carte (frontmatter) rewritten on top, nothing else.
- **Fiches, as knowledge.** Written by Maggie with `memory_write_fiche` (`app/memory/fiches.py`): the title is a true sentence, folders are hers (at most 3, shallow), the body is two lists the code writes — `## Ce qu'on sait` and `## Ce qui n'est plus vrai`. Each line: `texte — provenance · source[ · heure]`; provenance is `dit`, `observé` or `déduit`. A `dit` claim must cite an existing conversation file **and a minute present in it**; an `observé` one `app : <la donnée>`. A claim that stops being true is moved to the second list with its date and reason, never dropped. `déduit` claims are returned by `memory_open` as `a_annoncer`.
- **Encoding along the way (MAG-15).** `app/memory/encoder.py`, run by `run_memory_encoding` in the scheduler loop (never on the path of a turn): once a thread has been silent `MEMORY_ENCODE_AFTER_SECONDS` (300; the clock of its messages, not the dormancy of MAG-12), the fast model reads what was said since the thread's `encoded_up_to` and the pass writes the carte of the passage on top of its conversation file (`conversations.update_carte`: resume rewritten, moments / personnes / evoque added to, never dropped) and only the **obvious** fiches — claims `dit` by the owner at a minute of the passage. No arbitration: a doubt from the model (contradiction, two candidate fiches, a claim already moved to « n'est plus vrai ») leaves the fiche alone and says « laissée à la nuit » in `journal.md`; the night (MAG-159) decides. Idempotent: `context_repo.set_encoded` is a compare-and-set on the watermark, moments and claims are deduplicated, a failing thread is tried `MAX_ATTEMPTS` times then waits for a new message. Every journal line starts with « encodage au fil de l'eau », so the night's are told apart. Cost: `call_type="memory_encoding"`. Limits, on purpose: at most 20 threads per cycle (`find_to_encode`, oldest first); threads that existed when the watermark column was added start at their last message (the night covers them); a pass reads the newest 100 messages after the watermark; two pods may both pay the model for one thread (the dedup prevents duplicate writes, not the double cost); the resume of the carte is replaced by the model's whenever it returns one.
- **No category in code.** Nothing in `agent/app/` enumerates kinds of memory or names an entity such as « Personne »: the structure comes from the folders and titles Maggie chooses. A `grep` for it must stay empty.
- Tools: `memory_search`, `memory_open`, `memory_write_fiche` (`app/memory/tools.py`), all through `MemoryService`. The old `memory` table is read-only, used once by `app/memory/legacy.py` (`task agent:memory:import-legacy`, and on the first turn) to turn rows into fiches under `Ancienne mémoire/` and old messages into conversation files; what has no source says so.
- Nothing about an installed provider appears in `agent/` or `infra/`: S3 client only (`MEMORY_*` settings, documented in `infra/k8s/secrets.example.yaml`). `MEMORY_PROVIDER=fake` is the in-memory bucket with injectable outages (e2e, tests).

## Synchronisation
- Local copy ↔ bucket, both ways, rehydrated at boot (the pod has no persistent disk). **The owner's version always wins**: a file changed in the bucket is pulled; if both sides changed, Maggie's version goes to `Conflits/` and `journal.md` records both.
- Writes: local copy first, then the **outbox** (Postgres table, the only durable queue), pushed after the answer with a compare-before-push (`ETag`). Never `await` the network in a turn.
- Bucket down = degraded mode, not an error: Maggie answers from the local copy and the index, `MemoryService.notice()` tells her so (she says it if asked whether her memory is up to date), writes stay in the outbox, a `critical` log and `maggie_memory_degraded` fire. Back up → the outbox is pushed, nothing lost.

## The index
- Tables in `maggie_agent`: cards, evoked terms, aliases, links by id, bodies of the files (so recall works during an outage), French full-text search (`to_tsvector('french', …)`, GIN index in `run_migrations`). **Usage counters live in their own table, never in the files**, and survive a rebuild.
- Emptying the index loses nothing: `task agent:memory:rebuild` (or `MemoryService.rebuild`) restores everything from the files except the counters.
- Every query is filtered by `user_id`; ship a two-user isolation test (MAG-108).

## Recall at four levels (MAG-16)
Search stays on the foundation index — no embeddings. Code: `agent/app/memory/recall.py` (scoring), `agent_memory.py` (blocks), `prompt_cache.py` (`build_system`).
1. **Permanent profile**: `render_profile` lists the fiches (path + resume) — the `MEMORY_PROFILE_MAX` (80) most opened, sorted by path, then « … et N autres » — in a system block of its own. The text only changes when a fiche does, so the block stays cached.
2. **Automatic recall, every turn**: `recall_for_turn` scores the **cartes alone** (never the body) against the message: `evoque` and `alias` 3.0, a person 2.5, a moment on the day the message is about 3.0, a proper name in the title or resume 2.5, other title words 1.2, resume words 0.6; a conversation weighs ×0.7. Words are folded (accents, case, plural, elision, glued « l'UBU » → « lubu », fuzzy ≥ 0.85 for aliases). At least `MEMORY_RECALL_THRESHOLD` (2.5), at most `MEMORY_RECALL_MAX` (3); the current thread's file is left out. It is **bounded** by `MEMORY_RECALL_TIMEOUT_SECONDS` (0.8): past it, or on any error, the turn goes on without it. Same recall for chat, voice (same stream), proactions and the 5h planning (`about` = the day's events, read by `scheduler.planning_agenda`, never raising).
3. **Search by Maggie**: `memory_search` with `requete` and optional `termes` (≤ 5 associated terms she chooses, results merged).
4. **Opening**: `memory_open` for the detail.

Prompt order: stable (cached) → moment skills (cached) → profile (cached) → recalled cartes (not cached, changes every message) → volatile (notice, directives, date). A memory write never touches the first block. Four breakpoints at most with the tools.

Metrics: `maggie_memory_recall_seconds{source}`, `maggie_memory_recall_total{source,outcome}` (recalled | empty | timeout | error), `maggie_memory_recalled_cartes`, `maggie_memory_block_tokens{block}` (profile | recalled, 4 characters a token). Weights are constants in `recall.py`: tune them there, with a test case from real use.

## The night's upkeep (MAG-159)
`app/memory/night.py` (`NightKeeper`, `memory_night`), run by `_memory_night_loop` in the scheduler, never on the path of a turn. Due from `MEMORY_NIGHT_HOUR` (3, owner's timezone), once per local night; a pass cut off is due again at the next tick whatever the hour. Model: `settings.anthropic_model` (the encoder's fast model decides nothing hard), `call_type="memory_night"`.
Steps, in order, each tick spending at most `MEMORY_NIGHT_TICK_CALLS` (40) calls, a pass at most `MEMORY_NIGHT_MAX_CALLS` (200): **cartes** (encodes the threads still waiting, then only the missing cartes — a conversation's text is never rewritten) · **fiches** (one conversation per call, oldest first: create, complete, correct; the most recent word wins, the old wording stays dated under « Ce qui n'est plus vrai »; a doubt becomes a `question` on the fiche, shown as ❓ in the profile, never a silent decision) · **régularités** (a rule is written only with at least `MEMORY_NIGHT_MIN_PROOFS` (2) proofs in distinct conversations, each a real message of the owner) · **rangement** (rename keeping the id and the old title as alias, move, merge duplicates, split catch-alls — no claim lost or doubled) · **oubli** (the model judges, with age, uses and pointers as signals; a fiche set aside gets `archivee`, leaves the profile and the recall, its file and its conversation stay; a claim with no date is never offered) · **orphelines** (conversations get the `liens` of the fiches they justify; fiches with no source or that nothing points at are reported) · **rappels manqués** (last: see below).
Resumable and idempotent: `memory_night_run` keeps the status, the steps done and the report; `memory_night_seen` the (card, scope, digest of the messages) already handled, so a conversation is read again only if its messages grew; a unit failing twice is given up and listed. The **report** (kept in `memory_night_run.report`, no proaction journal exists yet — MAG-155) is summed up in one line of `journal.md`, « entretien nocturne du DATE », absent when nothing changed; every write of the night carries that label in the journal.

## Missed recalls (MAG-228)
« Tu aurais dû t'en souvenir » is recognised in conversation, no command: Maggie finds the fiche (`memory_search`; writes it first if it never existed), then `memory_log_miss(demande, chemin|souvenir)` records the case and she says the night will look into it. `app/memory/misses.py`.
- **A case is a file** of `Rappels manqués/AAAA-MM-JJ — <demande>.md` in the owner's folder: what he asked (`demande`), the fiche that should have come back (`attendue`, followed by `attendue_id`), what came back (`ressorti`), its state (`ouvert` · `vert` · `rouge`), a dated `## Historique`. It is synced like any file, **never indexed** (the recall can not surface it), written by the code only (`check_writable(miss=True)`); the owner removes a case by deleting the file. The same case said twice is one case, back to `ouvert`.
- **Each night, last step `rappels`**: every case is replayed against the index with the recall's own `rank`. Fiche back → `vert` (since when). Not back → the code **diagnoses** the cause, never the model: `fiche_inexistante` (created from the conversation where the owner said it — nothing he did not say; a fiche he deleted, known by its id, is never recreated) · `absente_index` (written again to be indexed) · `mise_de_cote` (`archivee` removed) · `evoque_pauvre` / `seuil_trop_haut` / `mauvaise_carte` (one model call proposes the missing associations for the fiche and for the fiches close to it — same people, ≥ 2 shared words, `evoque` under 3 terms; if it proposes nothing, the heart of the demand becomes the association). Then replayed again, at most 3 repairs per case per night.
- **Never silent**: each fix goes to `journal.md` (a write with its reason, plus the night's line: cause, « N/M rappel(s) manqué(s) rejoué(s) au vert », « retour au rouge » for a case that was green, « toujours rouge »). The numeric settings of the recall (threshold, weights) are never touched; only `evoque` grows.
- A fiche with a case is **not offered to the forgetting** (the owner expects it); a case follows its fiche through a rename (by id) and a merge. The case file is rewritten only when its content changes, so a quiet night writes nothing.
- The project's measure: the cases that no longer reproduce (`vert`), in the night's report and journal line.

## The web inspector (MAG-20)
The « Mémoire » tab of the « Maggie » settings reads and corrects the folder; no browser ever talks to the bucket. `app/api/memory_routes.py` (prefix `/memory`, bearer JWT, the folder of the token's user only: a path outside it is an unknown path, 404) over `app/memory/inspector.py`.
- **Routes**: `GET /tree` · `GET|PUT|DELETE /file?path=` · `POST /file/move?path=` · `GET /journal` · `GET|POST /sync` (state / relaunch) · `POST /rebuild` · `GET /misses` · `GET /export` (zip of the whole folder under `Mémoire/`, readable without the app).
- **The tree is the folder's** (the local copy mirrors the bucket), nothing regrouped. A file is a `fiche`, a `conversation`, a `generated` file (`LISEZMOI`, `AGENTS`, `sommaire`, `journal`) or a missed-recall `miss`.
- **What may change**: only fiches are edited, renamed, moved (the carte must stay readable: 400 otherwise; the `id` is kept, so recall and links follow). Conversations are append-only and generated files are Maggie's: both 409. Only fiches and missed-recall cases are deleted.
- **Every change goes through `MemoryService`** (`write` / `move` / `delete`): file, then index, then a `journal.md` line (« corrigé par le propriétaire depuis l'onglet Mémoire »), then the outbox. A PUT carries the `hash` it started from: 409 if the file moved on (Maggie, the night, the sync) — nothing is overwritten; without a `hash` the owner's version is written unconditionally (scripts). A move onto the same path is a no-op.
- **Live**: the service tells the web on the Mercure stream `memory` (`/memory/{userId}`, payload `{paths}`), coalesced over 0.4 s. The admin takes it from the Maggie settings page's own connection — a browser allows six per origin over HTTP/1.1, a seventh request waits forever; never open one more.
- **Sync state** (`GET /sync`): last success, pending writes with their paths, conflicts, and the bucket's outage with its age. The tab says it; an outage never blocks reading or correcting.
- Not done: re-importing an edited archive.

## The skills are files too (MAG-218)
What the owner teaches Maggie follows the same rules as what she knows. Code: `agent/app/skills/` (`document.py`: the Markdown format; `store.py`: `SkillFiles`).
- **A skill is a Markdown file** (frontmatter `name`, `description`, `tags`; body = the text) in `Compétences/` of the bucket — a folder of its own, **outside any user's folder**: the archive of the knowledge never holds a skill, and a skill never holds a user id (global until MAG-108). Identity = the frontmatter's `name`, never the file name; a frontmatter without `name` takes the file's stem; an unreadable file is left out of the index with a warning.
- **One mechanism, a second scope.** `SkillFiles` is a `MemoryService` whose scope is `paths.SKILLS_SCOPE` (`"skills"`) instead of a user id: same bucket client, outbox (key `skills`), compare-before-push, pull, `Conflits/`, degraded mode, boot rehydration. `paths.bucket_prefix`, `local_base` and `check_scope` map a scope to its folder; `MemoryService` itself only accepts user ids and never lists `skills` among its users. Do not write a second sync.
- **The `skill` table is a derived index.** Each pass that reached the bucket brings it in step with the files (`_reconcile_index`); rows whose file still waits in the outbox are kept. `SkillIndex.refresh()` catches up with the bucket (bounded wait, like a turn's) before loading the in-memory index from the table, so a file corrected by the owner reaches the next prompt. `SkillFiles.rebuild_table()` empties the table and rebuilds it from the files (never when there is no file to rebuild from).
- **Writes go to the file first**: `create_skill`, `update_skill`, `delete_skill` and the `/skills` routes call `SkillIndex`, which saves the file locally, queues it, then upserts the row. An update starts from the file's current text.
- **Migration.** On the first start (no skill file, nothing pending) the skills of the table are written as files, never over an existing file; afterwards the files rule — a skill deleted later does not come back from the table. A bucket that does not answer at boot leaves the table as it is.
- Directives stay in the database (out of scope). E2E: `e2e/web/tests/chat.spec.ts` « a skill corrected in its file… » drives the fake bucket through `/e2e/skills/*`.
