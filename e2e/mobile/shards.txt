# The Maestro journeys split across parallel emulators in CI (MAG-233).
#
# `N: flow flow …` — shard N runs these flows, in this order. `run.sh` reads it
# when `E2E_MOBILE_SHARD=N/<number of lines below>` is set, and `lint.sh` checks
# that every file in `flows/` is in exactly one shard, in the order of
# `config.yaml`'s `flowsOrder` — a flow missing here would never run in CI.
#
# Measured, not estimated (MAG-247): the `[Passed] <flow> (<time>)` lines of the
# `E2E Mobile journeys (phone n/3)` jobs, on three runs of the pipeline —
# main after MAG-242 (run 37310594639, no `09` yet), PR #169 (37467547103) and
# PR #168 (37489036346) — averaged:
#
#   02-voice-overlay     121 s   (124 · 122 · 116)
#   08-grocery-realtime  107 s   (111 · 116 ·  95)
#   01-login-chat         62 s   ( 69 ·  84 ·  34)   the first flow of a shard pays the cold app
#   04-calendar-import    48 s   ( 48 ·  54 ·  41)
#   09-finance-banks      36 s   (      38 ·  33)
#   05-deep-links         33 s   ( 35 ·  31 ·  34)
#
# That is ~407 s of flows, and a shard job costs ~255 s before its first flow
# (stack, emulator, APK install): the flows no longer decide much, the fixed cost does.
#
# Three shards and not two. Two would put ~205 s of flows on the slowest shard
# (02 + 04 + 05 against 08 + 01 + 09) against ~143 s with three, so the required
# `E2E Mobile (phone)` takes ~60 s longer, and the merge train, one pipeline at a
# time, waits that minute behind every mobile PR. What two would save is an emulator
# and a stack per device (three in the nightly), which on a public repository costs
# runner time, not money. The wall clock is what is scarce.
#
# Split by greedy balance: 02 alone (121 s, and the flow that hung once for 17 minutes
# stops holding two others), 08 + 09 = 143 s, 01 + 04 + 05 = 143 s. When a flow is
# added, re-read the figures from the latest run and move it where the sum is lowest.
1: 02-voice-overlay
2: 08-grocery-realtime 09-finance-banks
3: 01-login-chat 04-calendar-import 05-deep-links
